Ý tưởng A* trong 30 giây

A* "loang" từ ô start sang các ô kề, nhưng ưu tiên ô hứa hẹn nhất — được tính bằng hàm:

f(n) = g(n) + h(n)

g(n) = chi phí THỰC đã đi từ start → ô n
h(n) = ƯỚC LƯỢNG khoảng cách ô n → goal (đường chim bay, Euclidean)

Dùng heapq (priority queue) để luôn lấy ô có f nhỏ nhất ra xử lý. Nhờ h "hướng về đích", A* mở rộng ít ô hơn Dijkstra rất nhiều — cùng kết quả đường ngắn nhất.

Code chính (planner/astar.py)

def astar(grid, start, goal, allow_diagonal=True):
    open_set = [(0, start)]          # heap của (f, ô)
    g = {start: 0}                   # chi phí tốt nhất tới từng ô
    while open_set:
        _, cur = heapq.heappop(open_set)
        if cur == goal: return reconstruct_path(...)
        for nb in neighbors(cur, allow_diagonal):
            if grid[nb] == 1: continue          # vật cản — bỏ qua
            new_g = g[cur] + cost(cur, nb)      # 1 hoặc √2 nếu chéo
            if new_g < g.get(nb, inf):
                g[nb] = new_g
                heapq.heappush(open_set, (new_g + h(nb, goal), nb))

Ví dụ số

Start (2,2) → goal (17,17), bản đồ trống: đi chéo hết 15 bước chéo + √2·15 ≈ 21.2 m. Nếu cấm chéo (allow_diagonal=False): phải đi 15 ngang + 15 dọc = 30 ô. Cùng thử nghiệm ở notebook 01.

Điểm cần hiểu kỹ

  • Vì sao heuristic phải "không vượt quá thực tế" (admissible) thì A* mới tối ưu?
  • Đổi heuristic sang Manhattan (|dr| + |dc|) → đường dài hơn không? (GAP-6 dùng thủ thuật heuristic=0 để có Dijkstra)

Vấn đề: A* trả về ô vuông, xe không đi góc 90° được

A* cho dãy ô [(2,2), (3,3), (4,4)…] — khúc khuỷu, không có THỜI GIAN. Bước TRAJECTORY biến nó thành bảng điểm-đến-thời-điểm mà MPC cần bám:

t      x_ref   y_ref   yaw_ref  v_ref
0.00   1.00    1.00    0.785    1.0     ← yaw = hướng nhìn (rad)
0.35   1.35    1.35    0.785    1.0
0.70   1.70    1.70    0.785    1.0     ← mỗi dòng = 1 điểm MPC phải tới đúng lúc

3 bước xử lý (planner/trajectory.py)

  1. Nội suy theo độ dài cung: đi dọc đường A*, đánh dấu điểm mỗi ds = v·dt = 1.0 × 0.1 = 0.1 m (nội suy tuyến tính giữa 2 tâm ô)
  2. Tính yaw: góc hướng = atan2(y[k+1]−y[k], x[k+1]−x[k]) của 2 điểm liền kề
  3. Làm mượt: trung bình trượt (moving average) trên x, y, yaw — bỏ khúc gãy

Vì sao bước này quan trọng với MPC

  • MPC bám quỹ đạo này — nếu target_speed quá cao so với giới hạn lái, xe trượt khỏi quỹ đạo → RMSE tăng
  • Số điểm quỹ đạo quyết định thời lượng mô phỏng: 58 điểm × 0.1 s ≈ 5.8 s hành trình
  • Thí nghiệm: đổi target_speed 0.5 / 1.0 / 2.0 → quan sát RMSE và completion_time đổi thế nào

Vòng lặp MPC — "đi xe bằng cách nhìn trước"

Tại mỗi bước thời gian (mỗi 0.1 s), MPC làm 3 việc:

  1. Dự báo: lấy cửa sổ quỹ đạo tham chiếu ref[step : step+N+1] (N=10 bước = 1 giây phía trước)
  2. Tối ưu: giải bài toán QP — tìm chuỗi [steer, accel] sao cho tổng chi phí dưới đây nhỏ nhất:
cost = Σ (x_k − ref_k)ᵀ·Q·(x_k − ref_k)   ← phạt LỆCH quỹ đạo
     + Σ u_kᵀ·R·u_k                        ← phạt HÀNH ĐỘNG mạnh
     + 2·(x_N − ref_N)ᵀ·Q·(x_N − ref_N)    ← phạt lệch ở ĐÍCH

ràng buộc: |steer| ≤ 0.5 rad · |accel| ≤ 2 m/s² · 0 ≤ v ≤ 3 m/s
  1. Áp dụng: chỉ lấy phần tử đầu tiên của chuỗi tối ưu, bấm ga/lái, rồi lặp lại toàn bộ — gọi là receding horizon

Vì sao phải "iterative" (3 vòng tuyến tính hóa)?

Dynamics xe có cos(yaw), tan(steer) — phi tuyến, còn solver OSQP chỉ giải được bài toán LỒI. Giải pháp: tuyến tính hóa quanh quỹ đạo dự kiến bằng Jacobian, giải QP, lấy nghiệm làm quỹ đạo dự kiến mới, lặp lại 3 lần:

x_nom → Jacobian A=∂f/∂x, B=∂f/∂u → giải QP → nghiệm thành x_nom mới → lặp ×3

Xem hàm linearize() trong controller/iterative_mpc.py — chỉ ~20 dòng, tính đạo hàm riêng từng biến trạng thái.

Bảng tham số và tác động (configs/mpc_baseline.yaml)

Khi solver fail thì sao?

Nếu QP không hội tụ (config quá gắt), code fallback sang bộ điều khiển P đơn giản (đi theo góc tới waypoint) — robot vẫn di tiếp thay vì đứng im. Thấy log MPC solver failed = tín hiệu config có vấn đề.

Vòng lặp chính — 6 bước lặp đi lặp lại (simulator/run_simulation.py)

for step in range(max_steps):
  1. ref_window = ref[step : step+N+1]        ← "nhìn trước" N bước
  2. control = mpc.solve(state, ref_window)   ← MPC quyết định [steer, accel]
  3. control = clip(control)                  ← kẹp vào giới hạn vật lý
  4. collision = env.check_collision(x, y)    ← với bán kính 0.15 m
  5. log.append(t, x, y, yaw, v, steer, accel, collision, min_dist)
  6. state = vehicle.step(state, control)     ← bicycle model cập nhật vị trí
     nếu cách đích < 0.3 m → goal_reached = True, dừng

Mô hình xe — chỉ 4 dòng toán (controller/vehicle_model.py)

x(t+1)   = x(t)   + v·cos(yaw)·dt
y(t+1)   = y(t)   + v·sin(yaw)·dt
yaw(t+1) = yaw(t) + (v / L)·tan(steer)·dt    ← L = 0.3 m (wheelbase)
v(t+1)   = v(t)   + accel·dt                 ← dt = 0.1 s

Check va chạm hoạt động thế nào (simulator/environment.py)

Nhìn ô lưới chứa điểm (x, y) và các ô lân cận; tính khoảng cách thực tới tâm ô vật cản; so với ngưỡng radius + resolution/2 = 0.15 + 0.25 = 0.4 m.

⚠️ Điểm gây tranh cãi (GAP-1, P0): ngưỡng 0.4 m tính tới TÂM ô khiến robot cách tường 0.35 m vẫn bị tính là "va chạm" → số collision ở corridor/obstacles bị thổi phồng. Việc sửa ngưỡng này là bài tập nghiên cứu đầu tiên của nhóm (M4 phụ trách, xem mục GAP).

Agent là gì trong dự án này?

Hiện tại: agent = vòng lặp IF-ELSE thuần (agent/agent_loop.py) — đọc metrics, so với ngưỡng, chọn config từ danh sách có sẵn. Chưa "AI" theo nghĩa LLM.

Mục tiêu (GAP-8, P2): thay if-else bằng LLM — đưa metrics + mô tả scenario cho LLM, LLM ĐỀ XUẤT config mới (giải thích được tại sao), chạy lại, lặp cho tới khi đạt goal.

Vòng lặp hiện tại

trial = 0
while trial < max_trials:
  1. result = run_pipeline(scenario, config)          ← chạy mô phỏng
  2. m = result.metrics                                ← RMSE, collision…
  3. if m.collision == 0 and m.rmse < 0.2: break       ← đạt goal, dừng
  4. action = rule_engine(m)                           ← IF-ELSE quyết định
       nếu collision > 10 → đổi sang "conservative"
       nếu rmse > 0.5   → tăng Q, giảm R
       nếu quá chậm      → tăng max_steps
  5. config = apply_action(config); trial += 1

Ví dụ chạy thực tế

python agent/run_agent.py --scenario obstacles --max-trials 5

[trial 1] collision=23 rmse=0.41 → action: switch_to_conservative
[trial 2] collision=2  rmse=0.28 → action: increase_Q_x_y
[trial 3] collision=0  rmse=0.19 → GOAL REACHED ✅ (3 trials)

MCP server — "cổng an toàn" bắt buộc phải hiểu

MCP (Model Context Protocol) là lớp bọc giữa agent và pipeline: agent KHÔNG được gọi run_pipeline trực tiếp mà phải qua các "tool" MCP, mỗi tool:

  • validate tham số đầu vào (config có key thiếu? giá trị ngoài phạm vi? → từ chối, không chạy)
  • chặn hành vi nguy hiểm (viết file ngoài workspace, timeout quá dài)
  • ghi log mọi lần gọi → truy vết được agent đã làm gì
💡 Vì sao quan trọng: khi agent là LLM (bước GAP-8), nó có thể đề xuất config NỤC LY (max_steps=999999, bỏ ràng buộc va chạm). MCP chính là "rào chắn" đảm bảo máy chạy không phá project. Đây là chủ đề rất hợp thời (AI safety + agent orchestration).

Đọc hiểu code theo thứ tự

  1. mcp_server/server.py — các tool được expose
  2. mcp_server/validators.py — quy tắc validate config
  3. agent/agent_loop.py — vòng lặp if-else hiện tại

GAP-2 — Regression test map/scenario (P0, ~2h)

Bước 1: tạo tests/test_scenarios.py — test không cần pytest fixture gì cao siêu:

import yaml, pytest
from planner.astar import astar
from simulator.environment import Environment
from configs.loader import load_scenarios   # chỉnh theo hàm thật trong repo

@pytest.mark.parametrize("name", load_scenarios().keys())
def test_scenario_valid(name):
    s = load_scenarios()[name]
    grid = Environment.from_yaml(s.map).grid
    h, w = grid.shape
    for pt in (s.start, s.goal):
        assert 0 <= pt[0] < h and 0 <= pt[1] < w, f"{name}: {pt} ngoài biên"
        assert grid[pt] == 0, f"{name}: {pt} đè lên vật cản"
    path = astar(grid, s.start, s.goal)
    assert path is not None, f"{name}: A* không tìm được đường"

  • maze_small: 3–4 bức tường ngắn xen kẽ — test A* chọn đúng nhánh
  • Mỗi map thêm 1 scenario tương ứng vào configs/scenarios.yaml, rồi chạy pytest (test mới của GAP-2 sẽ tự kiểm tra map mới!)

GAP-6 — Dijkstra so sánh (~4h)

def heuristic(a, b, kind="euclid"):
    if kind == "none": return 0            # heuristic=0 → Dijkstra
    return ((a[0]-b[0])**2 + (a[1]-b[1])**2) ** 0.5

Đo trên 3 map: số node mở rộng (thêm counter vào astar), thời gian (time.perf_counter), độ dài đường. Kết quả mong đợi: cùng độ dài đường, Dijkstra mở rộng RẤT nhiều node hơn → đây là bảng so sánh đưa thẳng vào báo cáo.

Bạn là ai trong nhóm

Chủ nhân bước 4 trong FLOW — trái tim của dự án. MPC là thứ làm robot "thông minh" hơn path-following thường, và là nhân vật chính trong báo cáo NCKH.

GAP-5 — Vì sao aggressive tăng collision 24→67? (~3h)

Giả thuyết cần kiểm chứng: aggressive giảm R (phạt hành động) → solver sẵn sàng lái gắt để bám sát quỹ đạo → quỹ đạo thực đi sát tường → (cộng thêm lỗi ngưỡng ở GAP-1) collision tăng vọt.

  1. Chạy 2 variant trên corridor, đều --save-log:
python run_pipeline.py --scenario corridor --variant baseline --save-log
python run_pipeline.py --scenario corridor --variant aggressive --save-log
  1. Vẽ min_obstacle_distance theo thời gian cho cả 2 trên cùng 1 hình → aggressive sát tường hơn ở đoạn nào? Nhìn thấy ngay.
  2. Đếm: bao nhiêu % bước của aggressive có min_dist < 0.4 m? → ước lượng phần "false positive" (liên kết chéo với GAP-1 của M4).
  3. Kết luận + đề xuất variant aggressive_safe: giữ Q cao nhưng max_speed thấp hơn / R lớn hơn chút. Chứng minh collision giảm mà RMSE vẫn tốt.

Tiêu chí xong: 1 biểu đồ + 1 đoạn kết luận 10 dòng — kết quả NCKH thứ 2 của nhóm.

Quét horizon {3, 5, 10, 15, 20} (~2h)

  • Với mỗi giá trị: chạy basic_circle + obstacles, ghi RMSE + thời gian tính 1 bước MPC
  • Vẽ curve RMSE vs horizon và time vs horizon → tìm "điểm ngọt"
  • Thời gian giải tăng gần tuyến tính với N — kiểm chứng bằng số đo được

Nâng cao — ràng buộc vật cản trong QP (~4h, tùy chọn)

Thêm soft constraint: phạt nặng khi điểm dự báo nằm trong vùng đệm quanh vật cản (inflation 0.3 m) — chi phí dạng hinge max(0, d_safe − dist(x_k, obstacle))² nhân hệ số lớn. Đây là hướng CH-MPC nổi tiếng — nếu làm được có thể thành điểm nhấn báo cáo.

def suggest_with_llm(prompt: str):
    key = os.environ.get("LLM_API_KEY")
    if not key: return None            # không có key → fallback rule-based
    resp = call_llm_api(prompt, key)   # yêu cầu trả JSON thuần
    try: return json.loads(resp)
    except json.JSONDecodeError: return None   # LLM nói nhăng nhố → fallback

Bước 3: trong agent_loop.py: thử LLM trước, nhận None → dùng rule engine cũ. MCP validation luôn chạy sau cùng — LLM đề xuất gì đi nữa, config nguy hiểm vẫn bị chặn.

👤 M4 · 📁 simulator/environment.py · ⏱ ~2h · Robot bị tính va chạm khi còn cách vật cản 0.35–0.40 m → mọi số collision trong corridor/obstacles đang bị thổi phồng
Cách làm →

Ngưỡng hiện tại: radius 0.15 + resolution/2 0.25 = 0.4 m tính tới tâm ô vật cản.

  1. Trong check_collision(): đổi so sánh khoảng cách tới biên ô gần nhất thay vì tâm ô (trừ thêm resolution/2).
  2. Thêm metric mới safety_margin_violations: đếm số bước có min_obstacle_distance < margin (cấu hình được, vd 0.3 m).
  3. Chạy lại --batch --save-results, so sánh collision trước/sau — đây là kết quả nghiên cứu đầu tiên của nhóm.
